# 헌터 소집서 구현 범위

`mh:summon_scroll`은 최대 중첩 1개인 아이템입니다. 기본 획득은 별도 조합법이며 시작할 때 자동 지급하지 않습니다. 추격 중 살아 있는 참가 헌터만 사용합니다. 같은 차원의 살아 있는 다른 헌터 전원을 사용자 주변에 소집하고, 다른 차원 헌터에게는 안내만 보냅니다. 같은 차원에 이동할 헌터가 없으면 소비하지 않습니다.

기본값은 **러너 거리 350블록 초과**, **팀 공용 재사용 300초**, **팀 전체 경기당 2회**입니다. 거리에는 높이를 포함합니다. 사용자와 각 목적지 모두 제한 거리를 만족해야 하며, 정확히 350블록이면 거부합니다. 다른 차원의 러너는 거리 검사 대상에서 제외합니다. 러너가 접속하지 않았거나 부활 중이면 현재 위치를 확정할 수 없어 사용을 보류합니다. 사망·카운트다운·도주 대기·일시정지·종료·비참가자·러너 사용은 차단합니다.

## 위치 안전성과 성능

- 사용자 주위 반경 2~4블록, 현재 높이 ±2블록의 **이미 로드된 지형**만 검사합니다. 강제 청크 로딩, 추가 엔티티, 반복적인 광역 탐색은 없습니다.
- 목적지는 발·머리 두 칸이 공기이며 3×3 지지면이 알려진 바닐라 완전 블록이어야 합니다. 주변 용암·불·선인장·가루눈 등 위험 블록, 물에 잠긴 지면, 낙하성 블록, 반블록·계단·미확인 커스텀 지면은 거부합니다. 안전한 위치를 찾지 못하면 전원 이동을 취소합니다.
- 3×3 지지면까지 월드 경계 안이어야 하고, 다른 플레이어·계획된 목적지와 1.3블록 이상 떨어뜨립니다.
- 계획 중 중복 블록 읽기를 캐시합니다. 이동 직전에는 캐시 없이 지면·공간·러너 거리·차원·생존 상태를 다시 검사합니다.
- 기능 OFF이면 사용 검증에서 즉시 종료하고 지형 탐색을 수행하지 않습니다. 이전 실패의 데이터 복구는 안전 기능으로 유지합니다.

공식 문서의 [`Block.isSolid`](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/block?view=minecraft-bedrock-stable)는 사전 공개 표시가 있어 사용하지 않습니다. 정식 `typeId`, `isAir`, `isWaterlogged`와 보수적인 지면 목록을 사용합니다. 이동은 [`Entity.tryTeleport`](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/entity?view=minecraft-bedrock-stable)의 충돌 검사와 반환값을 확인합니다. 이 보수적인 판정은 실제로 설 수 있는 일부 좁은 지형도 거부할 수 있습니다.

## 중복 사용·실패·복구

한 호출 안에서 모든 위치를 계획하고 검증한 다음, 이동 전 위치와 고유한 소집서 표식을 저장합니다. 이동에 모두 성공하면 사용 횟수·경기 시계 기준 쿨다운을 확정하고 그 표식의 소집서 한 장만 소비합니다. 같은 틱에 중복 호출되거나 처리 중 다른 사용 요청이 들어오면 다시 실행하지 않습니다. 인벤토리 빈 칸은 필요하지 않습니다.

중간 이동이 실패하면 원래 차원·좌표·회전으로 전원 복귀를 시도하고 소집서를 보존합니다. 복귀할 플레이어가 없거나 이동 자체가 실패하면 복구 저널을 유지하고 새 사용·라운드 초기화를 차단합니다. 자동 재시도는 최대 100틱마다 수행하며, 재접속·관리자의 명시적 재시도는 즉시 실행합니다. 확정된 거래의 소집서 표식이 남아 있으면 재접속 시 한 번만 정리합니다.

원래 위치의 청크가 로드되지 않으면 복귀가 계속 실패할 수 있습니다. 공식 [`tryTeleport` 문서](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/entity?view=minecraft-bedrock-stable#tryteleport)는 이 실패 조건을 명시합니다. 같은 문서의 `teleport`에는 미로드 청크를 반드시 로드한다는 보장이 없으므로, 안전 검사를 생략하는 강제 이동이나 상시 청크 로딩을 대안으로 사용하지 않습니다.

관리자는 복구 메뉴에서 **재시도** 또는 **현 위치 유지·실패 거래 정리**를 선택할 수 있습니다. 수동 정리는 경기 일시정지·로비·종료 상태에서만 허용하고, 기록된 관련자 전원의 접속·생존 및 현재 위치의 지면·공간·경계·겹침을 재검사합니다. 따라서 관련자를 넓고 안전한 지면으로 이동시킨 뒤 현재 위치를 그대로 수용할 수 있습니다. 이 선택은 원래 위치로 복귀시키지 않으며 아이템을 추가 지급하거나 소비하지 않습니다. 환급 상태가 불명확한 경우 자동 보상을 하지 않는다는 안내를 확인한 후 진행합니다. 마지막 관리자·거래·확인 위치 기록은 라운드 초기화 후에도 보존됩니다. 확정 기록을 먼저 저장하고 표식을 제거하므로 같은 정리를 재실행해도 아이템을 복제하지 않습니다.

**보장하지 않는 부분:** Minecraft는 플레이어 인벤토리 저장과 월드 동적 속성 저장을 하나의 디스크 트랜잭션으로 제공하지 않습니다. 프로세스 강제 종료·저장 장치 오류가 두 저장 사이에 발생하는 경우까지 원자적으로 보장했다고 주장하지 않습니다. 표시가 남은 소집서나 충돌한 환불 칸은 임의로 삭제·덮어쓰기·추가 지급하지 않고 사용을 막습니다. 이런 비정상 복구 상태는 관리자 확인 대상입니다. 일반적인 호출 중 실패와 재접속 복구는 자동 시험으로 검증합니다.

## 통합 API

`createSummon(world, system, () => state, {tell, report, save, inventory, isDead, isAdmin})`

- `use(player)`: 아이템 컴포넌트 `onUse`/`onUseOn`에서 호출합니다. 성공 시 `true`입니다. 별도 아이템 차감 코드를 추가하지 않습니다.
- `joined(player)`: 참가자 초기 입장·부활 처리 후 복구를 시도합니다.
- `recover(force = false)`: 미완료 복구가 있을 때 호출합니다. `hasPending()`을 확인한 뒤 저빈도 게임 루프에서 호출할 수 있습니다. 관리자 재시도는 `true`를 전달합니다.
- `pendingRecovery()`: 거래 식별자·종류·관련자·대기 원위치·환급 불명확 여부를 반환합니다. 확인 UI는 이때 받은 `token`을 보관합니다.
- `resolveAtCurrent(admin, expectedToken)`: 관리자 확인 UI에서 저장한 거래 식별자를 전달합니다. 권한·거래 일치·현재 안전 상태를 다시 확인한 뒤 현재 위치를 수용합니다. `isAdmin`이 전달되지 않으면 수동 정리를 허용하지 않습니다.
- `reset()`: 이전 복구가 완료되면 팀 상태를 초기화합니다. **반환값이 false이면 시작·리셋을 진행하지 않아야 합니다.**
- `hasPending()`: 진행 중인 복구 저널 유무입니다.

`state.summon`에 `round`, `uses`, `readyAt`, `serial`, `transaction`, `lastRecovery`가 저장됩니다. 기존 전적·러너 생명·추적 상태는 변경하지 않습니다.

검증: 모의 환경 26개 시험 통과. 미로드 복귀 실패의 수동 출구, 권한·일시정지·접속·지면 검사, 오래된 확인 거부, 환급 중복 방지, 저장 실패·재접속 재생과 재시도 간격을 포함합니다. 실제 Minecraft 다중 클라이언트 소집, 강제 종료 시험, FPS/TPS 실측은 이 모듈 단독 작업에서는 수행하지 않았습니다. 최종 통합 QA 보고서를 기준으로 확인하세요.
