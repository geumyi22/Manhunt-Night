# Manhunt Night v1.5.1 — 실제 실행·부분 성능 측정 기록

검증일: **2026-11-14 KST**. 이 문서는 **v1.5.1의 과거 실측 기록**입니다. 이후 버전의 실행 검증이나 인원 확장 검증으로 재사용하지 않습니다.

**판정: 부분 실기 확인. 3~4인 정식 경기 E2E와 전체 성능 QA는 미완료입니다.** 실제 엔진 TPS와 호스트 프로세스 메모리·CPU를 측정했습니다. FPS와 게임 네트워크는 미측정입니다.

## 1. 대상과 보존

- Windows Bedrock 26.63, 설치 패키지 `1.26.6301.0`, 실제 프로세스 `Minecraft.Windows`에서 실행했습니다.
- 기존 v1.5.1 배포 `.mcworld`를 복사한 **QA 2026-11-14 PERF SOLO** 월드만 시험했습니다. 입력 SHA-256은 `ee595db8b14df9d8ab2424c4b2553efb4fd601ebf99ad018c033efeec48863ee`입니다.
- 시험 사본의 월드 이름과 BP/RP UUID를 분리하고, 사본의 스크립트에 읽기 전용 TPS 관찰 코드를 추가했습니다. 시험 사본 생성 시 원본 DB를 바이트 단위로 복사했고 배포 입력 파일이 변경되지 않았음을 확인했습니다. 실제 플레이에 따른 저장은 시험 사본에만 발생합니다. 생성 기록은 [probe-world.json](qa/2026-11-14-runtime-v151/probe-world.json)에 있습니다.
- 기존 BSLB Dreamy 설정을 유지한 환경입니다. 셰이더·영상 설정을 통제한 비교 벤치마크가 아닙니다. 시험 도우미도 배포 게임 코드에 추가하지 않았습니다.
- 시험 종료 시 실제 게임 UI의 저장 및 종료를 수행하고 월드 목록 복귀를 확인했습니다. 사용자 플레이 월드·설정·기존 릴리스 자산을 덮어쓰지 않았습니다.

## 2. 관측과 사용자 보고의 구분

개인 계정명 대신 **클라이언트 A(호스트)**, **클라이언트 B(추가 접속자)**로 표시합니다.

| 항목 | 확인 근거 | 확인 범위와 한계 |
|---|---|---|

| B의 접속·이탈·재접속 | 호스트 채팅에 참여→이탈→참여 표시, 관찰 로그의 인원 1→2→1→2 | 호스트에서 연결 상태 변화 확인. 기존 경기의 헌터 역할 복구·제작 상태 보존은 검증하지 않음 |

## 3. 실제 TPS 관찰

시험 사본에서 100틱마다 `system.currentTick` 차이와 `Date.now()` 벽시계 시간 차이를 기록했습니다. **구간별 합계 틱 ÷ 합계 초**로 가중 평균을 계산했으며, 20을 조금 넘는 값을 임의로 20에 맞추지 않았습니다.

완전한 JSON **140개**를 추출했습니다. 시작 지연이 포함된 첫 샘플과 관찰된 인원·단계 전환 구간 6개를 집계에서 제외했습니다. 로그 끝의 잘린 JSON 1개도 제외했습니다. 첫 유효 관찰 시각은 **18:33:23.298 KST**, 마지막 완전한 관찰 시각은 **18:44:53.308 KST**입니다.

| 관찰 인원·단계 | 집계 샘플 | 유효 구간 합계 | 가중 평균 TPS |
|---|---:|---:|---:|
| 1명 접속 · 로비 | 14 | 69.998초 | 20.0006 |
| 1명 접속 · 1인 연습의 유예/진행 | 36 | 179.988초 | 20.0013 |
| 2명 접속 · 기존 1인 연습 진행 | 39 | 194.992초 | 20.0008 |
| 2명 접속 · 로비 | 44 | 220.007초 | 19.9994 |

위 시간은 선택된 구간들의 합이며 모두 연속된 동일 조건 시험을 뜻하지 않습니다. 관찰된 값은 약 20 TPS이지만, 두 명의 역할을 갖춘 실제 경기·3~4인 동시 기능·장시간 안정성을 입증하지 않습니다. 벽시계 기반이므로 시스템 시간 보정과 포커스·메뉴·로딩의 영향을 고려해야 합니다.

## 4. 호스트 메모리·CPU

동일 호스트 프로세스를 약 1초 간격으로 읽어 두 번 기록했습니다. 두 시간창 모두 접속·재접속 때문에 **인원 1/2명이 섞여 있습니다**. 두 번째 창은 로비 복귀도 포함합니다. 따라서 첫 창을 순수 1인, 두 번째 창을 순수 2인 성능으로 비교하지 않습니다.

| 측정창 | 실제 수집 | 관찰 상태 | WorkingSet 중앙 / 최대 | Private Bytes 중앙 / 최대 | 전체 CPU 시간가중 평균 |
|---|---|---|---:|---:|---:|
| `solo-memory` | 180.659초 · 178샘플 | 1/2명, 유예/진행 혼합 | 2366.43 / 2797.20 MiB | 4041.41 / 4530.17 MiB | 23.53% |
| `two-clients-memory` | 180.173초 · 177샘플 | 1/2명, 진행/로비 혼합 | 2872.27 / 2914.46 MiB | 4570.83 / 4636.14 MiB | 22.52% |

WorkingSet은 프로세스의 물리 메모리 사용량 지표이고 Private Bytes는 전용으로 할당한 가상 메모리 지표입니다. 서로 더하지 않습니다. CPU는 호스트의 논리 프로세서 20개 전체를 100%로 계산했습니다. GPU 메모리나 B 기기의 사용량은 측정하지 않았습니다.

표의 중앙값은 CSV에서 다시 계산했습니다. 원시 CSV 및 최초 sampler JSON도 그대로 보존합니다. 개별 메모리 샘플에 역할·인원을 추정하여 붙이지 않았으며, 이 수치로 성능 개선·메모리 누수 없음·권장 사양 충족을 주장하지 않습니다.

## 5. FPS·네트워크와 로그

- **FPS 미측정:** 설치된 NVIDIA FrameViewSDK의 PresentMon `1.9.12728.0`에서 도움말은 확인했으나, 실제 게임 PID 대상으로 시도한 캡처 3개가 모두 종료 코드 1로 끝났습니다. CSV와 프레임 샘플은 0개입니다. 현재 토큰의 ETW 권한 문제가 가능한 원인이지만 내부 실패 원인은 확정하지 않았습니다. 관리자 승격·보안 설정 변경·다른 측정 세션 중지는 수행하지 않았습니다.
- **게임 네트워크 미측정:** 접속 성공을 대역폭·지연·패킷 손실 측정으로 간주하지 않습니다. 프로세스 IO나 다른 앱이 포함된 어댑터 트래픽을 게임 수치로 사용하지 않았습니다.
- Manhunt 로드 기록을 확인했고 검사한 로그에서 `Scripting error`는 0개였습니다. 다만 Manhunt 로딩 이전 시점의 `Lighting` 오류 1개가 있으므로 전체 Content Log가 무오류라고 주장하지 않습니다. 해당 오류의 원인·팩 귀속은 미확정입니다.
- 원본 Content Log 전체, 로컬 계정 경로, 참가자 닉네임은 공개 증거에 포함하지 않습니다. 필요한 Manhunt 로드 기록과 개인정보 없는 QA 행만 추출했습니다.

## 6. 공개 증거와 남은 검증

공개 파일은 [qa/2026-11-14-runtime-v151](qa/2026-11-14-runtime-v151)에 있습니다. [SHA256SUMS.txt](qa/2026-11-14-runtime-v151/SHA256SUMS.txt)로 원시 CSV·요약·TPS JSON·시험 사본 생성 기록·시작 제한 스크린샷의 무결성을 확인할 수 있습니다. 집계 결과는 [summary.json](qa/2026-11-14-runtime-v151/summary.json), 원시 TPS는 [tps-samples.jsonl](qa/2026-11-14-runtime-v151/tps-samples.jsonl)입니다.

남은 항목은 실제 역할이 배정된 정식 경기에서 헌터별 추적기, 동시 투척 제작, 소집, 차원 이동, 경기 상태의 재접속 복구, 헌터 기기별 수신기 카메라, 부활·헌터 처치·드래곤 승패, 기본 20/40분 동작 및 장시간 성능입니다. 이 기록만으로 [Issue #3](https://github.com/geumyi22/Manhunt-Night/issues/3)을 완료 처리하거나 Stable로 승격하지 않습니다.

향후 버전에서 인원 규칙을 바꾸더라도 **이 문서의 v1.5.1 실측값과 2명 시작 제한 관측을 새 버전의 통과 결과로 바꾸지 않습니다.**
